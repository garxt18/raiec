================================================================================
1. PROJECT OVERVIEW
================================================================================

BACKGROUND:
North Western Railway's Civil and Construction unit handles numerous tender 
estimates daily from IREPS (Indian Railways E-Procurement System). Each tender 
PDF contains hundreds of line items requiring verification against official rate 
references (CPWD DSR and IRUSSOR). The manual process was time-consuming and 
error-prone, requiring significant officer expertise.

OBJECTIVES:
- Automate PDF parsing of IREPS tender documents
- Implement intelligent rate matching against reference databases
- Provide directional variance analysis with smart thresholds
- Integrate AI-powered risk assessment
- Build self-learning LAR (Last Accepted Rate) dataset
- Create officer approval workflow with role-based access
- Develop real-time dashboard and analytics

KEY FEATURES:
✓ Multi-format PDF parsing (continuous numbering, mixed NS items)
✓ Exact code + fuzzy description matching (Trigram Similarity)
✓ Directional thresholds (5% WARN, 10% FAIL, at/below = OK)
✓ Rule-based checks + LLM assessment (hybrid AI)
✓ Self-learning LAR dataset (grows with approvals)
✓ JWT authentication (Admin/Officer roles)
✓ Real-time dashboard with live stats
✓ LAR intelligence insights
✓ Bulk PDF ingest capability
✓ No-build frontend (vanilla HTML/CSS/JS)

   tender (1:N) → schedule (1:N) → schedule_entry (1:N) → breakup_item

   - lar_record: Last accepted rates
   - irussor_item: IRUSSOR reference data
   - dsr_item: CPWD DSR reference data
   - app_user: User authentication

4. SECURITY FLOW
   1. User submits credentials to /api/auth/login
   2. Password verified with BCrypt comparison
   3. JWT generated with username/role claims (8-hour expiration)
   4. Token stored in localStorage on client
   5. Future requests include token in Authorization header
   6. JwtAuthFilter intercepts, validates token, sets SecurityContext
   7. Role-based access enforced on endpoints

   ROLES:
   ADMIN: All permissions + bulk ingest + reference imports
   OFFICER: Upload, view, approve/reject tenders

5. COMPLETE TENDER ANALYSIS WORKFLOW
================================================================================

STAGE 1: PDF UPLOAD & INGESTION
--------------------------------------------------------------------------------
FRONTEND (step1-upload.html):
- Drag-and-drop or file picker
- Client-side validation (PDF type, size < 30MB)
- FormData with file
- POST to /api/tenders/upload

BACKEND (TenderService.ingestPdf):
1. Check duplicate by tender number
2. Extract text with Apache PDFBox
3. Parse structure with TenderPdfParser:
   - NIT header (tender no, date, dept, total amount)
   - Identify schedules (A/B/C/D sections)
   - Parse line items (serial, description, quantity, unit, rate, amount)
   - Detect rate breakups (material/labor/equipment costs)
   - Classify items: SCHEDULED or NON_SCHEDULED
4. Extract NS items, generate LAR codes (NS001, NS002, NS003...)
5. Save to database with cascade operations
6. Set initial status = UPLOADED
7. Return tender ID to frontend

RESPONSE:
- Store tender ID in sessionStorage
- Auto-navigate to step2-ocr-extract.html

TECHNOLOGIES: Apache PDFBox, Regex patterns, Spring Data JPA, FormData API


STAGE 2: OCR EXTRACTION & VERIFICATION
--------------------------------------------------------------------------------
FRONTEND (step2-ocr-extract.html):
- Retrieve tender ID from sessionStorage
- GET to /api/tenders/{id}
- Receive full tender details with nested schedules/entries

RENDERING:
- Schedule tabs (A/B/C/D)
- Table columns: S.No, Description, Quantity, Unit, Rate, Amount
- Color coding: Blue (Scheduled items), Yellow (Non-Scheduled items)

USER VERIFICATION:

TRANSITION:

TECHNOLOGIES: Fetch API, sessionStorage, Template literals, CSS Grid


STAGE 3: RATE MATCHING ENGINE
--------------------------------------------------------------------------------
FRONTEND (step3-rate-match.html):
- POST to /api/tenders/{id}/rate-match
- Display loading spinner during processing

BACKEND ALGORITHM (RateMatchService.evaluate):
For each ScheduleEntry in tender:

1. DETERMINE REFERENCE SOURCE
   - SCHEDULED items: Try DSR first, then IRUSSOR
   - NON_SCHEDULED items: Use LAR dataset

2. EXACT CODE MATCH (Primary Strategy)
   - Query repository by itemCode and edition
   - If found, use reference rate directly

3. FUZZY DESCRIPTION MATCH (Fallback Strategy)
   - Normalize both descriptions (lowercase, remove special chars)
   - Generate trigrams (3-character sequences)
     Example: "cement" → ["cem", "eme", "men", "ent"]
   - Calculate similarity: intersection / union
   - Threshold: > 0.60 (60% similarity required)
   - Select best match above threshold

4. CALCULATE VARIANCE
   variance = ((quoted_rate - reference_rate) / reference_rate) × 100

5. APPLY DIRECTIONAL THRESHOLDS
   variance ≤ 0%: "OK" (at or below reference)
   0% < variance ≤ 5%: "OK" (acceptable small overage)
   5% < variance ≤ 10%: "WARN" (moderate overage, needs attention)
   variance > 10%: "FAIL" (significant overage, reject recommended)

6. BUILD RESPONSE
   RateMatchItem {
     itemCode, description, quotedRate
     referenceRate, referenceSource (DSR/IRUSSOR/LAR/NONE)
     variance (percentage)
     verdict (OK/WARN/FAIL)
     confidence (for fuzzy matches only)
   }

RESPONSE SUMMARY:
- List of all matched items
- Aggregate counts: OK: X, WARN: Y, FAIL: Z
- Overall pass/fail determination

FRONTEND RENDERING:
- Color-coded table:
  * Green rows: OK items
  * Yellow rows: WARN items
  * Red rows: FAIL items
- Reference source badges (DSR/IRUSSOR/LAR)
- Variance percentages displayed
- Confidence scores for fuzzy matches
- Summary panel: "45 OK, 3 WARN, 2 FAIL"

EXAMPLE CALCULATION:
Quoted Rate: ₹550 per unit
Reference Rate: ₹500 per unit
Variance: ((550 - 500) / 500) × 100 = 10%
Verdict: WARN (at 10% threshold)

TECHNOLOGIES: Custom Trigram Algorithm, Spring Data JPA, BigDecimal, CSS Flexbox


STAGE 4: AI ANALYSIS
--------------------------------------------------------------------------------
FRONTEND (step4-ai-analysis.html):
- GET to /api/tenders/{id}/ai-summary
- Show loading state

BACKEND - RULE-BASED CHECKS (AiAnalysisService):

1. Rate Deviation Analysis
   - Count items by verdict (OK/WARN/FAIL)
   - Calculate percentages
   - Flag if >20% items are WARN/FAIL

2. LAR Lowest Rate Check (Non-Scheduled items only)
   - Compare against historical LAR dataset
   - Flag if current quote is NOT the lowest on record
   - Show historical lowest rate for comparison

3. Math Verification
   - Verify: quantity × rate = amount
   - Check breakup sums: material + labor + equipment = total
   - Tolerance: 1% for rounding differences

4. Duplicate Detection
   - Find items with identical/similar descriptions but different rates
   - Flag potential errors or inconsistencies

Each check returns:
- checkName (e.g., "Rate Deviation Analysis")
- status (PASS/FAIL)
- message (detailed explanation)
- itemsAffected (count)

BACKEND - LLM ASSESSMENT (AiAssessmentService):

1. Build Context String:
   - Tender summary (number, date, total amount)
   - Rate match summary (OK/WARN/FAIL counts)
   - All rule-based check results
   - Top 5 highest variance items

2. Call LLM API:
   - Model: GPT-4o-mini
   - Temperature: 0.3 (consistent analytical output)
   - Max tokens: 400 (concise summary)
   - Timeout: 20 seconds
   - System prompt: "You are a tender analysis expert for railway construction..."

3. Parse LLM Response:
   - narrative: Risk assessment summary (2-3 sentences)
   - recommendation: APPROVE / REVIEW / REJECT
   - riskLevel: LOW / MEDIUM / HIGH

4. Fallback Strategy (if LLM unavailable or fails):
   - Use AiAssessmentNarrator.fallbackSummary()
   - Rule-based risk derivation:
     * All checks pass + no FAIL verdicts = LOW risk
     * Some WARN verdicts or 1-2 check fails = MEDIUM risk
     * Multiple check fails or >3 FAIL verdicts = HIGH risk

RESPONSE STRUCTURE:
AiAnalysisResponse {
  checks: [array of rule-based check results]
  assessment: {
    narrative: "This tender shows..."
    recommendation: "APPROVE"
    riskLevel: "LOW"
  }
}

FRONTEND RENDERING:
- Checks Section: Each check as card with PASS/FAIL badge
- Assessment Section:
  * Risk level badge (colored: green=LOW, yellow=MEDIUM, red=HIGH)
  * Narrative text
  * Recommendation badge (green=APPROVE, yellow=REVIEW, red=REJECT)
- Overall summary panel

USER ACTION:
- Reviews AI analysis results
- Clicks "Send to Officer Review"
- Navigates to step5-officer-review.html

TECHNOLOGIES: OpenAI-compatible client, Java Streams, CompletableFuture, CSS Grid


STAGE 5: OFFICER REVIEW & DECISION
--------------------------------------------------------------------------------
FRONTEND (step5-officer-review.html):
- Retrieve tender ID from sessionStorage
- Parallel requests:
  * GET /api/tenders/{id} (full tender details)
  * GET /api/tenders/{id}/rate-match (rate comparison)
  * GET /api/tenders/{id}/ai-summary (AI analysis)

CONSOLIDATED VIEW (3 Tabs):
- Tab 1: Tender Summary (header info, schedules, line items)
- Tab 2: Rate Match Results (table with color-coded verdicts)
- Tab 3: AI Analysis (checks + LLM assessment)
- Decision Panel: Approve (green) / Reject (red) buttons

APPROVE WORKFLOW:
User clicks "Approve" → POST to /api/tenders/{id}/approve

Backend (TenderService.approve):
1. Load tender from database
2. Update status: UPLOADED → APPROVED
3. Extract all Non-Scheduled items
4. For each NS item:
   - Check if LAR code exists in lar_record table
   - If exists AND new rate < existing rate:
     * Update LAR record with lower rate (LOWEST RATE WINS)
     * Update acceptance count
   - If not exists:
     * Create new LAR record
5. Save all LAR records (batch operation)
6. Return success response

Example LAR Update Logic:
Existing LAR: NS001 "RCC Work M20 Grade" ₹500/cum
New approved tender: NS001 "RCC Work M20 Grade" ₹450/cum
Result: Update LAR to ₹450/cum (lower is better for railway)

REJECT WORKFLOW:
User clicks "Reject" → POST to /api/tenders/{id}/reject

Backend (TenderService.reject):
1. Update tender status: UPLOADED → REJECTED
2. Record rejection reason (optional)
3. No LAR dataset update
4. Return success response

POST-DECISION:
- Display success message
- Auto-redirect to dashboard after 3 seconds
- Dashboard updates with new tender status

TECHNOLOGIES: Spring @Transactional, Spring Data JPA, CSS Tabs, Promise.all()
